# Care Platform: готовность к RuStore и Android-площадкам

**Актуальность исследования:** 16 августа 2026 года

**Статус:** инженерный и продуктовый план; не подтверждает юридическую или production-готовность

## 1. Цель

Подготовить один безопасный Android-релиз Care Platform, который сначала проходит закрытый альфа-тест и модерацию RuStore, а затем может распространяться через другие практически значимые каналы без добавления лишних SDK и трансграничной телеметрии.

Care Platform остаётся concierge-MVP:

- семья оставляет заявку;
- координатор уточняет функциональные потребности;
- вручную предлагает 2–3 проверенных кандидата;
- объясняет выбор и сопровождает первый выход;
- приложение не оказывает медицинскую помощь и не формирует медицинские заключения.

Первый релиз не включает оплату, чат, рейтинги, медицинские документы и автоматическую интерпретацию сведений о здоровье.

## 2. Решение по каналам распространения

| Приоритет | Канал | Роль в запуске |
|---|---|---|
| P0 | RuStore | Первый российский магазин, закрытый альфа-тест и ручной go/no-go после модерации. |
| P0 | Huawei AppGallery | Закрывает устройства Huawei без Google Mobile Services. |
| P0, условно | Google Play | Максимальный дополнительный охват GMS-устройств, если доступна регистрация и верификация российского аккаунта. Только бесплатное приложение, без Play Billing. |
| P1 | Xiaomi GetApps | Значимый парк Xiaomi, Redmi и POCO; сначала подтвердить российский developer onboarding. |
| P1 | Samsung Galaxy Store | Значимый, но в основном дублирующий канал; требуется commercial seller verification и отдельная проверка Android-артефакта. |
| P1 | Прямой APK с официального сайта | Резерв для пилота и controlled rollout; требует собственной безопасной доставки и обновлений. |
| P2 | NashStore | Резервный российский каталог с недостаточно прозрачной публичной документацией разработчика. |
| P2 | RuMarket | Нишевый московский канал; публичный developer flow на дату проверки не найден. |

RuStore не должен зависеть от готовности зарубежных магазинов. Если Google Play Console недоступен, последовательность сохраняется: RuStore → AppGallery → прямой APK/другие OEM-магазины.

## 3. Аккаунт разработчика RuStore

RuStore документирует два основных типа аккаунтов для резидентов РФ:

- физическое лицо через VK ID;
- юридическое лицо или ИП через VK ID/VK Business ID с подписанием формы УКЭП.

Отдельного типа «самозанятый» в актуальной инструкции нет. Для бесплатного MVP физическое лицо может зарегистрироваться без подключения монетизации. Для долгоживущего Care Platform предпочтителен аккаунт фактического оператора ПДн и стороны пользовательского договора — ИП или юридического лица. Это позволяет согласовать правообладателя приложения, политику, договоры и будущую монетизацию.

До регистрации нужно определить:

1. юридического оператора ПДн;
2. правообладателя приложения;
3. владельца RuStore-аккаунта;
4. подписанта и наличие УКЭП/МЧД, если аккаунт корпоративный;
5. рабочий адрес поддержки.

Официальные инструкции:

- [Регистрация разработчика](https://www.rustore.ru/help/developers/developer-account/registration-developer)
- [Регистрация физического лица](https://www.rustore.ru/help/developers/developer-account/registration-developer/registration-fl)
- [Регистрация юридического лица или ИП](https://www.rustore.ru/help/developers/developer-account/registration-developer/registration)

## 4. Android-идентичность, сборка и подпись

RuStore принимает APK и AAB размером до 5 ГБ. Для первой версии нужны уникальный package name, рабочая release-сборка и цифровая подпись.

Для обновлений неизменны:

- package name;
- сертификат подписи;
- идентичность приложения.

`versionCode` каждой следующей production-, alpha- или beta-сборки должен увеличиваться.

### Текущее состояние Care Platform

Сейчас используется:

```text
dev.vnm0576.care_platform_app
```

Это допустимый технический `applicationId`, но выглядит как временный namespace. Первая публикация фактически закрепит его. До загрузки в любой магазин нужно принять формальное решение:

- оставить этот ID навсегда; либо
- выбрать окончательный namespace, связанный с реальным брендом/правообладателем.

Не следует менять package name после начала распространения.

### Единая стратегия артефактов

Из одного проверенного commit выпускать:

- `app-release.aab` — RuStore и магазины, поддерживающие bundle;
- подписанный universal `app-release.apk` — магазины с APK и официальный сайт.

Использовать один контролируемый сертификат приложения во всех каналах, где это допускается. Хранить production keystore вне Git, с двумя зашифрованными резервными копиями и зафиксированным SHA-256 сертификата.

Для AAB RuStore требуется отдельно подготовить PEPK-архив ключа подписи приложения и PEM-сертификат ключа загрузки.

Источники:

- [Публикация приложения](https://www.rustore.ru/help/developers/publishing-and-verifying-apps/app-publication)
- [Подпись APK](https://www.rustore.ru/help/developers/publishing-and-verifying-apps/app-publication/apk-signature)
- [Загрузка AAB](https://www.rustore.ru/help/developers/publishing-and-verifying-apps/app-publication/new-version-app/upload-aab)

## 5. RuStore SDK

Для публикации бесплатного приложения интеграция RuStore SDK не обязательна.

На первом релизе не подключать:

- Pay SDK — оплаты нет;
- Push SDK — нет подтверждённой необходимости;
- Review SDK;
- Remote Config;
- стороннюю рекламную или продуктовую аналитику.

Update SDK также не обязателен. Его можно рассмотреть отдельной задачей после первого релиза, если он корректно обрабатывает отсутствие или устаревшую версию клиента RuStore.

Официальный каталог: [RuStore SDK](https://www.rustore.ru/help/sdk)

## 6. Карточка RuStore

Минимальный комплект:

- название до 30 символов, совпадающее с названием после установки;
- тип «приложение»;
- предварительная категория «Объявления и услуги»;
- возрастная маркировка после контент-аудита, предварительно 0+;
- краткое описание до 80 символов;
- подробное русскоязычное описание до 4000 символов;
- минимум один рабочий контакт разработчика;
- иконка 512×512 с непрозрачным фоном;
- минимум три актуальных скриншота телефона;
- декларация категорий данных и чувствительных разрешений;
- тестовый аккаунт и инструкция модератору.

Карточка не должна обещать оплату, чат, рейтинги, медицинскую диагностику или другие отсутствующие функции. Скриншоты должны показывать фактический интерфейс и не содержать реальных ПДн.

Предварительно не выбирать категорию «Здоровье»: текущая функция — организация подбора услуги ухода. Категорию и 0+ нужно подтвердить письменным контент-аудитом перед подачей.

Источники:

- [Категории](https://www.rustore.ru/help/developers/publishing-and-verifying-apps/app-publication/new-version-app/category)

## 7. Разрешения и декларация данных

В основном Android Manifest сейчас явно заявлено только:

```xml
<uses-permission android:name="android.permission.INTERNET" />
```

Release-конфигурация запрещает cleartext-трафик. Это подходящий минимальный baseline.

Перед публикацией нужно проверить merged manifest готового release-артефакта, поскольку зависимости могут добавлять разрешения. На первом MVP не должны требоваться:

- геолокация;
- контакты;
- SMS и журналы звонков;
- микрофон;
- камера;
- широкий доступ к файлам;
- `CALL_PHONE`;
- `POST_NOTIFICATIONS`, пока push не включён.

Если позже потребуется фото, использовать Android Photo Picker. Для звонка открывать системный dialer через `ACTION_DIAL`.

В декларации RuStore указываются данные, собираемые приложением, backend, встроенными SDK и server-to-third-party потоками. Для Care Platform проверить как минимум:

- имя;
- телефон и e-mail;
- user ID;
- город/район;
- пользовательский контент;
- фото, если появится;
- функциональные сведения, которые могут характеризовать здоровье;
- диагностику и идентификаторы устройства, если они фактически собираются.

Источники:

- [Типы разрешений](https://www.rustore.ru/help/developers/publishing-and-verifying-apps/app-publication/new-version-app/declare-app-permissions/permission-types)
- [Декларация разрешений и данных](https://www.rustore.ru/help/developers/publishing-and-verifying-apps/app-publication/new-version-app/declare-app-permissions/how-to-declare-permissions)
- [Категории данных](https://www.rustore.ru/help/developers/publishing-and-verifying-apps/app-publication/new-version-app/declare-app-permissions/data-categories)

## 8. Правовые и продуктовые стоп-факторы

Публикация сборки не должна предшествовать готовности реального процесса обработки ПДн.

### Обязательные решения

1. Кто является оператором ПДн и стороной пользовательского договора.
2. Роль платформы: исполнитель подбора, агрегатор или информационный посредник.
3. Будет ли MVP собирать специальные категории ПДн о здоровье.
4. Кто и на каком основании вводит данные подопечного.
5. Как подтверждаются полномочия родственника или представителя.
6. Будет ли анкета сиделки публичной либо выдаваться определённым клиентам.
7. Какие поля профиля видны до и после подтверждения подбора.
8. Сроки хранения заявок, анкет, аккаунтов, логов и backups.
9. Как реализуются отзыв согласия, запрос данных и уничтожение.
10. Какой российский SMS/e-mail-провайдер используется и какие данные он получает.

### Рекомендуемый безопасный baseline

- пользователи, создающие заявки и анкеты, — 18+;
- публичного каталога сиделок нет;
- до получения согласия подопечного заявка обезличена;
- медицинские документы и свободный клинический текст не собираются;
- сокращённые профили выдаются только выбранным аутентифицированным заказчикам;
- контакты раскрываются после отдельного действия и по необходимости;
- зарубежная аналитика, crash reporting и рекламные SDK отсутствуют;
- push, если появится, содержит только нейтральный текст;
- правила сервиса, политика и согласия являются отдельными документами и отдельными действиями пользователя.

Обычная галочка «Согласен с правилами платформы» недостаточна для всех целей. Для специальных категорий ПДн может потребоваться письменное электронное согласие с формализованной простой электронной подписью: идентифицированный аккаунт, соглашение о ПЭП, OTP, snapshot/version/hash документа, время и доказательство подтверждения. Схему должен проверить российский профильный юрист.

Публичная политика обработки ПДн должна быть доступна по HTTPS до регистрации и из приложения. Оператор должен до начала production-обработки выполнить применимые уведомительные и организационные обязанности перед Роскомнадзором.

## 9. Удаление аккаунта и данных

RuStore в изученных публичных правилах не устанавливает отдельную кнопку удаления аккаунта как самостоятельное обязательное поле. Законная обработка всё равно требует рабочего процесса доступа, исправления, отзыва, блокирования и уничтожения.

Нужны:

- in-app-путь «Управление данными»;
- публичная HTTPS-форма для пользователя, утратившего доступ;
- повторная аутентификация;
- объяснение состава и сроков удаления;
- отдельные операции отзыва согласия и удаления аккаунта;
- охват Auth, PostgreSQL, Storage, индексов, push-токенов, обработчиков и резервных копий по утверждённой политике;
- журнал и доказательство уничтожения.

Этот механизм одновременно подготовит приложение к требованиям Google Play для приложений с аккаунтами.

## 10. Тестирование и публикация RuStore

Рекомендуемая последовательность:

1. Собрать release AAB и universal APK с production-like российским staging.
2. Проверить подпись, ABI, merged manifest, native `.so`, домены и отсутствие секретов.
3. Пройти функциональное тестирование на реальных устройствах.
4. Подготовить синтетический модераторский аккаунт со всеми сценариями.
5. Провести закрытый alpha-тест RuStore, доступный до 2000 тестировщиков по VK ID.
6. После модерации выбрать ручную публикацию.
7. Провести отдельный go/no-go: backend, документы, поддержка, удаление, наблюдаемость, incident response.
8. Для последующих обновлений применять поэтапную публикацию.

## 11. Репозиторный release-readiness checklist

### Идентичность и подпись

- [ ] Утверждены бренд, Android label и окончательный `applicationId`.
- [ ] Создан production keystore вне Git.
- [ ] Сделаны две защищённые резервные копии.
- [ ] Зафиксирован SHA-256 сертификата.
- [ ] Определена единая стратегия ключа для магазинов.
- [ ] `versionCode` увеличивается монотонно.

### Android-артефакт

- [ ] `flutter analyze` и `flutter test` проходят.
- [ ] Собраны release AAB и universal APK из одного commit.
- [ ] Проверены release signature и certificate fingerprint.
- [ ] Проверены `minSdk`, `targetSdk`, `compileSdk` и ABI.
- [ ] Проверены merged manifest и все exported components.
- [ ] Нет debug endpoint, cleartext URL и server secrets.
- [ ] Проверено обновление поверх предыдущей подписанной версии.

### Сеть и зависимости

- [ ] Составлен реестр Flutter/Android SDK, доменов и получателей.
- [ ] Production Auth, PostgreSQL, Storage, backups и логи находятся в РФ.
- [ ] Нет Firebase, Sentry, Crashlytics, рекламной аналитики и attribution SDK.
- [ ] Токены, телефоны и анкеты не попадают в логи.
- [ ] Public/publishable key имеет минимальные права через RLS.

### ПДн и документы

- [ ] Определён оператор ПДн.
- [ ] Подано применимое уведомление Роскомнадзору.
- [ ] Политика опубликована на HTTPS и доступна до регистрации.
- [ ] Правила, политика и согласия разделены.
- [ ] Фиксируются версия, hash, время и субъект каждого согласия.
- [ ] Выбран законный сценарий данных подопечного и представителя.
- [ ] Не собираются медицинские документы и свободный клинический текст.
- [ ] Реализованы отзыв, доступ, исправление и уничтожение.
- [ ] Подготовлена точная декларация данных RuStore.

### Модерация и карточка

- [ ] Backend стабилен и доступен модератору.
- [ ] Есть синтетический тестовый аккаунт и пошаговый сценарий.
- [ ] Название и иконка совпадают в приложении и карточке.
- [ ] Есть минимум три актуальных скриншота без ПДн.
- [ ] Описание отражает только выпущенную функциональность.
- [ ] Категория и возрастная маркировка подтверждены аудитом.
- [ ] Есть действующий e-mail поддержки.
- [ ] Проведён закрытый alpha-тест.
- [ ] Для первой версии выбрана ручная публикация.

## 12. Критические стоп-факторы текущего проекта

До первой загрузки в RuStore блокируют:

1. не утверждён окончательный package name;
2. production keystore и release fingerprint не созданы и не проверены;
3. не определён юридический оператор ПДн/владелец store-аккаунта;
4. отсутствуют готовая публичная политика и отдельные согласия;
5. не выбран законный сценарий данных подопечного и представителя;
6. не реализован полный процесс удаления/отзыва;
7. не развёрнут и не проверен production-like российский backend;
8. не выполнен аудит release manifest, ABI, SDK и сетевых endpoint;
9. нет проверенного модераторского аккаунта;
10. не подготовлены карточка, иконка, скриншоты и декларация данных.

Положительная база уже есть:

- Android и Web scaffolding;
- только разрешение `INTERNET` в основном manifest;
- cleartext запрещён в release;
- код не допускает молчаливую release-сборку с debug-ключом;
- нет Firebase, Sentry и рекламно-аналитических SDK;
- Pay и Push SDK не нужны для текущего MVP.

## 13. Следующие отдельные задачи

Не объединять их в один PR:

1. принять продуктовые и юридические решения из раздела 8;
2. утвердить бренд и Android application ID;
3. спроектировать consent evidence и удаление данных;
4. подготовить российский staging и live-integration тесты;
5. создать защищённый signing process;
6. добавить автоматизированный Android release audit;
7. подготовить тексты и графику карточки RuStore;
8. зарегистрировать аккаунт фактического оператора;
9. провести закрытый RuStore alpha;
10. после go/no-go выполнить ручную публикацию.
